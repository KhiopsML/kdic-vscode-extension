# Khiops Dictionary Language Support for VS Code

VS Code extension providing syntax highlighting, IntelliSense, hover documentation, built-in structural validation, and optional native Khiops validation for [Khiops](https://khiops.org) dictionary files (`.kdic`).

Built-in validation is intentionally best-effort and structural. The native Khiops parser remains authoritative for complete semantic validation, especially rules whose operand scopes are not documented, joins, and complex block contents.

> **Note** — This extension was entirely generated by AI using the official [Khiops dictionary documentation](https://khiops.org/api-docs/kdic/dictionary-files/) as the reference specification. It follows the documentation of **Khiops 11.0.2**, the version documented on khiops.org (checked on 2026-11-25).

## Features

### Syntax Highlighting

- **Keywords**: `Dictionary`, `Root`, `Unused`
- **Native types**: `Categorical`, `Numerical`, `Text`, `Date`, `Time`, `Timestamp`, `TimestampTZ`
- **Advanced types**: `Entity(...)`, `Table(...)`, `TextList`, `Structure(...)`
- **Derivation rule function calls**
- **String literals** (double-quoted, with `""` escape) and **backtick-quoted identifiers** (variable names and computed table references)
- **Comments** (`// ...`) — line comments only, no block comments
- **Metadata annotations** (`<key>`, `<key=value>`, `<key="value">`)
- **Special constant** `#Missing`
- **Numbers** (integer, decimal, scientific notation)

### IntelliSense Completions

Context-aware completions:

| Context                     | Suggestions                                                                  |
| --------------------------- | ---------------------------------------------------------------------------- |
| Top level (outside `{}`)    | `Dictionary`, `Root Dictionary`                                              |
| Inside a dictionary block   | All types (`Categorical`, `Numerical`, …), `Unused`, `Entity(…)`, `Table(…)` |
| After `=` (derivation)      | All derivation rule functions with signatures and documentation              |
| After `Entity(` or `Table(` | Dictionary names declared in the current file                                |
| After `<` (metadata key)    | `DateFormat`, `TimeFormat`, `TimestampFormat`, `TimestampTZFormat` — the key of the line's type first |
| Numerical operand of a rule | `#Missing`, when the cursor follows `(` or `,` and the rule expects a `Numerical` there |
| Operand of a rule           | The variables and variable blocks of the dictionary the operand is resolved in (the secondary table for aggregations, `TableSelection`, `GetValue*`, …), those of the expected type first; each `.` goes one scope up. Documents over 1,000,000 characters are completed from the line only |

**Covered rule categories**: Numerical/Categorical comparisons, Logical operators, Data conversion, Math, String, Date/Time/Timestamp/TimestampTZ, Table aggregation, Table management, Vector, Hash Map, Data preparation, Predictor (Classifier/Regressor), Interpretation, Reinforcement, Coclustering, Sparse blocks (CopyBlock, GetBlock), Text sparse (TextWords, TextNgrams, TextTokens, …), Preparation sparse (DataGridBlock, DataGridStatsBlock, DataGridCellBlock), Table partition (Partition, TablePartition, TablePartitionCount, …), Table block (TableBlockMean, TableBlockEntropy, …).

### Hover Documentation

Hovering over any keyword, type, or derivation rule function name shows inline documentation:

- Keywords and types: usage description and syntax
- Derivation rules: function signature and description

### Type Checking

Real-time diagnostics for derivation rule calls, including the calls nested in other calls:

- **Return-type mismatch**: the declared variable type does not match the function's return type.
  > `Categorical x = TableCount(t);` → error on `Categorical` (TableCount returns `Numerical`)
- **Argument-type mismatch**: an argument variable, plain or between backquotes, has the wrong type for its parameter position.
  > `TableCount(Class)` where `Class` is `Categorical` → error on `Class` (expected `Table`)
- **Nested call result**: the result of a call used as an argument must be a type the enclosing rule accepts at that position. Each nested call is also checked against its own parameters, and the return type of the whole derivation is compared with the declared variable.
  > `Sum(Amount, Concat(Name, "x"))` → error on `Concat` (it returns `Categorical`, `Sum` expects `Numerical`)
- **Constant-type mismatch**: a string constant where a `Numerical` is expected, or a number or `#Missing` where a `Categorical` is expected.
  > `Concat("a", #Missing)` → error on `#Missing` (`Concat` expects `Categorical`)
- **Rules with a variable number of arguments**: `Sum(Numerical value1, ...)`, `Concat(Categorical value1, ...)` and the like check every extra argument against the type before `...`. Calls that do not have the arguments the registered signature describes (fewer, or more for a rule without `...`) are not checked.
- **Operand of a secondary table**: in `TableMean(DNA, Pos)`, `Pos` is looked up in the dictionary of `DNA`, and its type is checked there.
  > `TableMean(DNA, Char)` where `Char` is `Categorical` in the dictionary of `DNA` → error on `Char` (expected `Numerical`)
- **Scope operator**: in `TableSelection(DNA, EQc(Char, .MostFrequentChar))`, `.MostFrequentChar` is looked up in the scope above, and `..X` two scopes above. A call behind a dot (`.TableMode(DNA, Char)`) is evaluated there too. Dots that go beyond the outermost scope are an error, as in Khiops.
  > `Sum(.Age, 1)` at the top level → error on `.` (there is no scope above)
- **Undeclared variable argument**: a derivation argument variable is not declared in the dictionary its scope refers to (the current one, or the dictionary of the table).
  > `Sum(Revenue, MissingVar)` → warning on `MissingVar` (likely typo)
- **Key field not Categorical**: every field listed in a dictionary's key must be declared `Categorical`.
  > `Numerical id;` in a `Dictionary Foo (id)` → error on `Numerical`
- **Unknown dictionary reference**: `Table(X)` or `Entity(X)` where dictionary `X` is not declared anywhere in the file.
  > `Table(Burbu) vehicles;` → error on `Burbu`
- **Word after a variable name**: a second word where `;` is expected. Any word, a keyword included, is a valid name, so the error is on the second one.
  > ``Date Categorical `DAT_DEB_ENG` ;`` → error on `DAT_DEB_ENG`
- **Statement that does not start with a type**: a misspelled type or `Unused`, a word before the type, or a word that is not a type after `Unused`. Other lines that no pattern recognizes are only warnings, since an error would stop Khiops from running on save.
  > `Categorial Name;`, `Unuset Numerical x;`, `Unused TargetTable Entity(T) t;` → error on the word that is not a type
- **Names used twice**: two variables, a variable and a variable block, two blocks or two dictionaries with the same name (case matters).
  > `Numerical Age;` twice in a dictionary → error on the second `Age`
- **Space at the end of a name**: a dictionary or block name between backquotes that starts or ends with a space.
- **Variable block keys**: each member of a block needs a `VarKey`, an integer between 1 and 1,000,000,000 or a non-empty string, of the same kind in the whole block and not used twice; `DefaultNumericalValue` and `DefaultCategoricalValue` must fit the type of the block.
  > `Numerical Words1; <VarKey=1>` and `Numerical Words2; <VarKey=1>` in one block → error on the second `1`
- **Multi-table keys**: a `Root` dictionary has a key; a root is not the target of an internal relation; along `Table(X)` and `Entity(X)` relations the key of `X` is not shorter than that of the dictionary that holds the variable, and is longer when a `Table` leads to a dictionary that has relations of its own; an external entity `Entity(X) name [key]` points to a root dictionary, with as many keys.
  > `Root Dictionary Customer (Id)` with `Table(Usage) Usages;` where `Usage` has no key → error on `Usage`
- **Derived key field**: fields listed in a dictionary's key must not be derived from a rule.
- **Undeclared key field**: every dictionary key must refer to a declared variable.
- **Name length**: dictionary and variable names are limited to 128 characters.
- **Format metadata**: `DateFormat`, `TimeFormat`, `TimestampFormat` and `TimestampTZFormat` must follow a variable of their own type (`Date`, `Time`, `Timestamp`, `TimestampTZ`), be given a string value, and name one of the [formats Khiops documents](https://khiops.org/api-docs/kdic/date-rules/) (also [time](https://khiops.org/api-docs/kdic/time-rules/), [timestamp](https://khiops.org/api-docs/kdic/timestamp-rules/) and [timestamp with time zone](https://khiops.org/api-docs/kdic/timestamp-tz-rules/)).
  > `Time t; <DateFormat="DD/MM/YYYY">` → error on `DateFormat` (it applies to `Date` variables)
  > `Date d; <DateFormat=12>` → error on `12` (a string value is expected)
  > `Date d; <DateFormat="yyyy-mm-dd">` → error on the string (not a Khiops date format)

Operands of a table or entity rule are checked in the dictionary they are resolved in: the current one, or, for the operands that Khiops resolves in the secondary table (`TableMean(DNA, Pos)`), the dictionary that the first operand's `Table(X)` or `Entity(X)` points to. Operands whose scope is not documented in the rule catalogue, and those of a rule whose first operand is not a variable, are not type-checked by the built-in validator; native Khiops validation remains authoritative.

### Grammar Validation

Real-time diagnostics for structural grammar issues:

- **(Error)** Non-comment, non-metadata content after `;`
- **(Error)** Missing `;` at the end of a complete variable declaration
- **(Error)** Missing `;` after the closing `}` of a dictionary block
- **(Error)** Unclosed, unmatched, or incorrectly nested braces, parentheses, and external-key brackets
- **(Error)** Malformed metadata, variable names, or derivation constants
- **(Error)** Invalid variable-block members or closing declarations
- **(Warning)** Lines that do not match any known kdic grammar pattern — use `//` to mark non-kdic content

Allowed after `;`: metadata annotations `<key>`, `<key=value>`, `<key="value">` and `//` comments.

VS Code turns every carriage return of a file into a line break in the editor, whereas Khiops only treats `\n` as one: an isolated `\r` inside quoted text is legal in a `.kdic` file. For such a file the editor text no longer matches the file, so the built-in diagnostics are turned off for it and the native Khiops check is the one to rely on. Saving rewrites the file with ordinary line breaks, and built-in diagnostics resume.

### Native Khiops Validation (Optional)

When a Khiops binary is available, the extension can run native Khiops parsing diagnostics and show them in the Problems panel.

Built-in diagnostics are produced while editing and Khiops runs on an eligible save only when the built-in validator reports no errors. Built-in warnings do not prevent the native run.

Configuration settings:

- `kdic.enableKhiopsValidation` (`true` by default): enable or disable native Khiops checks
- `kdic.runKhiopsOnAutoSave` (`true` by default): also run native Khiops on auto-save; set to `false` for very large dictionary files
- `kdic.enableDebugTraces` (`false` by default): enable verbose Khiops trace logs in the Output panel
- `kdic.khiopsPath` (empty by default): path to the Khiops executable or its containing directory. Directory resolution uses `MODL` on macOS, `MODL_openmpi` on Linux, and `MODL.exe` on Windows. On macOS, use `/Applications/Khiops.app/Contents/Resources/bin/MODL` (file) or `/Applications/Khiops.app/Contents/Resources/bin` (directory).

Binary discovery order:

1. `kdic.khiopsPath`
2. `%KHIOPS_HOME%\\bin\\MODL.exe` on Windows
3. `/Applications/Khiops.app/Contents/Resources/bin/MODL` on macOS
4. `/usr/bin/MODL_openmpi` on Linux

If no binary is found, the extension falls back automatically to built-in validation.

Recognised structural patterns include:
- Dictionary headers with optional key list and metadata: `Root Dictionary Foo (key1, key2) <meta> {`
  - After the dictionary name, only a key list `(…)`, metadata tags `<…>`, and/or an opening brace `{` are valid
- Key list on its own line: `(SampleId)`
- Variable declarations: `[Unused] Type[(Class)] name [= derivation] ;`
- Sparse sub-block syntax: `{` / `} BlockName [= derivation] ;`
- Variable blocks: members must be `Numerical`, `Categorical`, or `Table` with one compatible type, and individual members cannot have derivations
- Multi-line derivations (continuation lines after unclosed `(` or trailing `=`)
- Metadata-only lines: `<key>`, `<key=value>`, `<key="value with > inside">`

## Installation

### From source (development)

```bash
npm install
npm run compile
```

Then press **F5** in VS Code to open an Extension Development Host with the extension loaded.

If you want native Khiops diagnostics, install the Khiops binary and configure `kdic.khiopsPath`. On Windows, `KHIOPS_HOME` is also checked automatically.

### Tests in a VS Code host

Run `npm test` for the standalone suite. To test the packaged extension in an isolated VS Code profile on macOS:

```bash
root="$(pwd)"
test_dir="$(mktemp -d /tmp/kdic-vscode-test.XXXXXX)"
npm run compile
./node_modules/.bin/vsce package --readme-path README.extension.md --out "$test_dir/kdic.vsix"
code --install-extension "$test_dir/kdic.vsix" --user-data-dir "$test_dir/user" --extensions-dir "$test_dir/extensions"
KDIC_VSCODE_TEST_EXTENSIONS="$test_dir/extensions" "/Applications/Visual Studio Code.app/Contents/MacOS/Code" \
  --extensionDevelopmentPath="$root/scripts/vscode-host-tests" \
  --extensionTestsPath="$root/scripts/vscode-host-tests/run.js" \
  --user-data-dir="$test_dir/user" --extensions-dir="$test_dir/extensions" \
  --disable-workspace-trust --skip-welcome --skip-release-notes
```

The temporary profile and packaged extension remain in `test_dir` for inspection.

To also check the extension on a directory of real dictionaries (for example the `LearningTest` corpus), set `KDIC_VSCODE_CORPUS` to it in the environment of the second command. Each `.kdic` file is opened, never saved, and the diagnostics VS Code shows must be those of the built-in validator; the real Khiops binary is then run on a few fixtures to check that its errors land on the right lines. It takes about ten minutes for 3,300 files. Rebuild and reinstall the packaged extension first: the test runs the installed copy, not the sources.

| `src/validator.ts`, `src/validation/` | Built-in validation: one small module per kind of check |

| `scripts/` | Unit tests (`npm test`), smoke-test CLI, VS Code host tests |
| `openspec/specs/` | Behavior specifications |

`.github/copilot-instructions.md` describes the modules and the validation pipeline in more detail.
Run `node scripts/smoke-test.js [--errors-only] [directory]` after `npm run compile` to validate every `.kdic` file of a directory.

The Khiops test corpus (LearningTest, kept outside this repository) is the regression reference. [corpus-expectations.json](corpus-expectations.json) lists the files of that corpus that have diagnostics: for each, the exact diagnostics, whether the Khiops binary itself accepts or rejects the file, and an optional note. Pass it to the smoke test:

```bash
node scripts/smoke-test.js --expected corpus-expectations.json [directory]         # report only what changed (exit 1 if anything did)
node scripts/smoke-test.js --update-expected corpus-expectations.json [directory]  # rewrite it; Khiops is run on the files it does not know yet
```

A file that Khiops accepts and that has a built-in *error* is a false positive of the validator, to fix or to explain in its `note`. Paths are relative to the corpus directory, and the default directory is `~/Dev/LearningTest`.

### Package as `.vsix`

```bash
npm install
npm run compile
npm run package
# produces khiops-kdic-0.1.3.vsix
```

Install the `.vsix` via **Extensions → Install from VSIX…** in VS Code.

## Grammar Reference

Full specification: [Khiops dictionary documentation](https://khiops.org/api-docs/kdic/dictionary-files/), as published for **Khiops 11.0.2**. A dictionary written for another version of Khiops may use constructs that the built-in checks do not know; the native Khiops validation then has the last word.

### Formal grammar (summary)

```
// File may start with an optional version header
#Khiops <version>

// Dictionary block
['//' <label>]
['//' <comment>]*
['Root'] 'Dictionary' <name> ['(' <key-fields> ')'] [<metadata>]
'{'
    ['//' <comment>]*
    [ <variable> ]*
    ['//' <internal-comment>]*
'};'

// Variable
['//' <comment>]*
['Unused'] <type> <name> ['[' <join-key> ']'] ['=' <derivation>] ';' [<metadata>] ['//' <label>]

// Metadata (one or more, space-separated)
<key>  |  <key=value>  |  <key="value">
```

### Quick syntax reference

```kdic
#Khiops 11.0.0

// Single-table dictionary
Dictionary Iris
{
    Numerical   SepalLength ;
    Numerical   SepalWidth  ;
    Numerical   PetalLength ;
    Numerical   PetalWidth  ;
    Numerical   PetalArea   = Product(PetalLength, PetalWidth) ;
    Categorical Class       ; // target variable
};

// Multi-table dictionary (star schema)
Root Dictionary Customer (id_customer)
{
    Categorical id_customer ;
    Categorical Name        ;
    Entity(Address) Address ; // 0-1 relationship
    Table(Usage)    Usages  ; // 0-n relationship
    Numerical       nbUsages = TableCount(Usages) ;
};

Dictionary Address (id_customer)
{
    Categorical id_customer  ;
    Categorical City         ;
};

Dictionary Usage (id_customer)
{
    Categorical id_customer ;
    Categorical Product      ;
    Numerical   Cost         ;
    Timestamp   PurchaseDate ; <TimestampFormat="YYYY-MM-DD HH:MM:SS">
};

// External table (explicit join key in brackets)
Dictionary Service (id_customer, id_product)
{
    Categorical     id_customer ;
    Categorical     id_product  ;
    Entity(Product) Product [id_product] ; // explicit join on id_product
};

Root Dictionary Product (id_product)
{
    Categorical id_product ;
    Categorical Name       ;
    Numerical   Price      ;
};
```
